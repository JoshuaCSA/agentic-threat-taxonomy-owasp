SCOPEWhat this covers

A threat modelling aid. An architect walks it against an agentic system design and enumerates what can go wrong. It is organised for coverage during design review, not for audit scoring or control mapping.

Four OWASP Top 10 lists cover agentic AI. Between them they hold 40 entries that use different names for the same threat, mix three different kinds of thing in one numbering scheme — adversary acts, missing controls, resulting harms — duplicate across lists without cross-references, and range from stable release to incubator draft. The result cannot be walked against a design.

Safety and security are both in scope

The register covers adversarial threats and autonomous failures alike, separated by an origin attribute rather than by two models. At the deployment layer the two converge: the same over-permissioned architecture produces both, and the same controls govern both. A model that cannot describe the Replit production-database deletion — no adversary, catastrophic outcome — is incomplete for agentic systems.

Model-level safety — refusal training, alignment of the base model — is out of scope; that is the model provider's work. The training phase in the reference architecture is not an exception: what it covers is the supply of training inputs and the integrity of the resulting artifact, not whether the model is well aligned.

STRUCTUREThree layers, four relations

Every source entry is assigned to exactly one layer by a single test. Where an entry conflates layers, it is split and mapped to each.

WEAKNESS— enables → THREAT— produces → IMPACT— chains back to T ·  and  T — enables → T

Four relations: W → T, T → I, I → T, T → T. There is no W → I — it is derived by composing the first two, never stored.

LayerDefinitionTest

Impacts chain back into threats

W → T and T → I are many-to-many. I → T chaining is what makes multi-step agentic attacks expressible; without it the model describes single hops only. One injected instruction escalating across three surfaces:

RP.1   prompt injection             a poisoned document reaches the context
  ↓
I4     unexpected code execution    the injected instruction runs generated code
  ↓
IA.2   privilege escalation         that code widens the agent's own scope
  ↓
I1     sensitive data disclosure    records the task never needed are read
  ↓
TA.1   tool misuse                  a legitimate outbound call carries them
  ↓
I5     cascading failures           downstream agents compound the error

Six distinct entries, two I → T hops, three surfaces — RP, IA, TA — terminating in I5. Both hops — I4 → IA.2 and I1 → TA.1 — are enumerated edges. The chain terminates at I5, so it does not itself show I5 chaining onward; the enumeration supplies that separately, I5 → RP.1 and I5 → RT.1. Without the relation, this is six unrelated register entries.

The lethal trifecta appears here as the middle move, I1 → TA.1: private data in context, an untrusted instruction already in play, and an outbound tool to carry it. Written as a standalone path it reads RP.1 → I1 → TA.1 → I1 and produces I1 twice — once when data is retrieved into context, once when it leaves the boundary. Those are different events with different reporting consequences, and the impact layer does not distinguish them.

Both hops here — I4 → IA.2 and I1 → TA.1 — are among the 13 I → T edges, which are enumerated with the impacts that carry them in the impact register.

Kind — how to read the column above

position

Occupies one place in the data flow, and a threat there compromises that component. Scoped out if the system does not have it — an agent that delegates to no other agent has no XA.

plane

Has no single location: every component holds a credential, is supplied by someone, and runs somewhere. Never scoped out — there is no agentic system without identity, supplied components, or a runtime, so these nine threats are in scope before you assess a single position.

SC is the one surface with no position in the runtime flow at all — it appears only in the upper band of the diagram, and its four threats are assessed against registries, pipelines and CI rather than against the running system. Two other build-time threats sit on surfaces that do have runtime positions: KM.2 and RT.3.

Injection reach · rust · relation to RP.1

inj entry

This threat is prompt injection — the entry point everything else converges on.

inj

Injection reaches it — directly, or through an impact injection itself produces. Unconditional: it holds in any deployment. Six threats.

inj?

The same, but only where the agent holds a capability in that domain — a property of the deployment, not of the injection. Two threats — preconditions below.

via

Runs the other way: this threat delivers injected instruction into RP.1. Four threats, drawn as the inbound edges at the end of this section.

The chip records whether, the T → T diagram records how. A chip says injection gets there; whether the route is a single step or passes through an impact first is what the arrowheads and dotted lines at the end of this section distinguish. Reading the chip as a claim of directness is the mistake it is worded to prevent.

Eight threats carry no injection chip at all. They are not the whole out-of-reach set, which is eleven: the three via-only threats — TA.2, XA.1, SC.1 — carry a chip and are still beyond injection's reach, because via runs the other way. All eleven fail for structural reasons rather than incidental ones; see the distribution note at the end of this section.

RP.1 and RP.2 differ by scope, not mechanism. They share every vector. ASI01 draws the line itself: it is “distinct from LLM01 in that the impact is redirected goals, planning, and multi-step behaviour rather than a single altered response.” RP.1 compromises a response; RP.2 compromises the plan and survives to the next step.

RP.2 and RP.3 are the adversarial and autonomous versions of one failure. Both end with the agent pursuing a goal nobody asked for — in one someone put it there, in the other proxy optimisation drifted into it. The controls follow the distinction: instruction/data separation against hijack, objective specification and behavioural bounds against misgeneralisation.

The name misleads, and is kept anyway. LLM01's own definition lists seven vectors — direct user input, retrieved content, tool output, image, audio or video content, intermediate reasoning, persistent memory — of which six are not prompts. Teams routinely sanitise the user input field and believe the surface is covered. Instruction injection is the more accurate term and is retained as an alias.

“Indirect injection” has no entry of its own. It is the relation between a via threat and RP.1, and the register replaces the term with an answer to indirect through what — KM.1 a poisoned memory or RAG store, TA.2 a tool description, XA.1 a spoofed agent message, SC.1 a hostile extension. Four named surfaces with four owners and four controls, in place of one word.

SC spans both build phases. SC.2, SC.3 and SC.4 apply to training inputs — datasets, base weights, training and conversion pipelines — as well as to application components, and SC.3 and SC.4 additionally apply to the model artifact itself, because what crosses into the application phase is a supplied component like any other. What injection reach shows. Nine of the twenty threats are injection outcomes; eleven are not, and the eleven fail for structural reasons. Six are build-time — KM.2, all four of SC, and RT.3 — and injection reaches no build-time threat at all. The remaining five are runtime but outside the instruction channel: RP.3 and RP.4 need no adversary, XA.1 is network-layer, RT.2 is query-volume, and TA.2 runs the other way. Injection owns the runtime meaning layer almost completely and touches nothing else.

The two inj? preconditions

ThreatInjection reaches it only where…
IA.1the agent can influence which identity it acts under — dynamic delegation, agent-selected roles, or credentials carried in the context window rather than bound out-of-band
IA.2there is a scope-granting path the agent can invoke — self-service permission requests, a consent flow it can drive, or a tool holding admin capability

Both are the same rule: conditional reach is gated by capability possession, not by anything about the injection. The six inj threats are unconditional because their capability is inherent — the model always reads its context, always has some tool, always faces a human. These two are optional in a given deployment, which gives an assessment rule: if your agent has a tool in that domain, promote inj? to inj for your system.

Threats chain into threats

Twelve T → T edges, every one touching RP.1, and all twelve derived — none curated. Which side of the hub a threat sits on is the relation kind, so the edges carry no attribute of their own.

Nothing in this relation is curated. The four inbound edges derive from via, which is defined as delivering injected instruction into RP.1, so the target is fixed by the definition. The eight outbound edges derive from inj and inj?. The composed paths derive from T → I and I → T. There is no hand-maintained list anywhere in it, and so nothing that can go stale without another view catching it.

Direct and composed are not competing classifications. Where both exist they are two different attacks on the same pair, and the difference is where you can intervene. RP.1 → I4 → XA.2 is an injected instruction that runs code which registers an unsanctioned agent — sandbox the interpreter and that route closes. RP.1 → XA.2 is an injected orchestrator delegating a task beyond a sub-agent's authorised scope, which the sandbox does not touch. Recording only one of the two is how a threat model comes to claim a control works when it half-works.

RP.2 is the only threat injection reaches by exactly one route. Every other threat on the right has at least two. That makes goal hijack the single place where containing an impact achieves nothing at all and the control has to sit at the instruction channel — and it is a derived fact now, not a curated judgement. It replaces the old three-edges-versus-five-reach split, which asked which escalations to admit and answered inconsistently: TA.1 and XA.2 carry identical attributes and were classified oppositely.

RP.1 composes to all thirteen I → T edges, because it produces five of the six impacts and the sixth, I6, is a pure sink. Two of the thirteen point back at RP.1 itself: I2 → RP.1 is why prompt extraction matters — once the guardrail wording is known, injection can be written to evade the guardrails it just read — and I5 → RP.1 is how injection propagates across a fleet, a corrupted upstream output read downstream as instruction.

KM.1 is the only threat on both sides, which is what makes the cycle real rather than rhetorical. An agent that can write to its own memory, or to the index it later retrieves from, can be injected into poisoning its own corpus; the poisoned entry then delivers instruction on every subsequent read. Every other inbound threat delivers once.

The direct routes are reasoned, not sourced. None of the five OWASP documents models threat-to-threat escalation, so every direct edge rests on analysis of the mechanism — an injected instruction that says remember that X, or delegates beyond scope, or calls a tool without bound. The composed paths inherit the same caveat one layer down, since the I → T edges they compose are themselves reasoned rather than measured. What changed is that the judgement is now visible per route instead of hidden inside a decision about which escalations to admit.

This is also the answer to the obvious challenge — why is RP.1 an entry at all, when eight threats can be reached from it? Because five of the eight carry a both origin and occur with no adversary present, so injection is one route among several rather than the route; and because RP.1 reaches five of the six impacts by paths that pass through none of them. RT.3 is not among the eight, and used to be. It carried a conditional injection marker alongside an auto origin, and those cannot both hold — injection is adversarial by definition, so an entry cannot be adversary-free and injection-reachable at once. Where an injected instruction does make an agent start an unsanctioned container, the event is TA.1 tool misuse and the deployment is its result: the path is RP.1 → TA.1, never RP.1 → RT.3. Injection therefore reaches no build-time threat at all, without exception.

REGISTER · WWeaknesses

Standing conditions. Each persists when nothing is happening, and each is the negation of a design principle. Click any row to see which threats it enables — 51 W → T edges in all — and which impacts those threats reach.

There is no direct W → I relation, and deliberately so. A weakness produces no harm on its own; it enables a threat, and the threat produces the harm. But the two edges compose, and the composition answers the question a control owner actually asks: if I fix this, which harms am I less exposed to? That is the second line inside each expanded row. Two weaknesses — W3 Insufficient Authentication & Authorisation and W4 Lack of Audit and Telemetry — reach all six impacts, and they are the only two that do. Reach is not the same as control leverage, and the register separates them: W7 No Governance ties W4 at the top of the leverage ranking with nine threats each, yet reaches only four impacts, because six of its nine sit in the build band and terminate in the same few outcomes. W3 enables seven and reaches all six. Fix by leverage and you touch the most threats; fix by reach and you close the most kinds of harm. At the other end, only W2, W3 and W4 reach I6 at all, because availability and cost loss comes solely from the RT surface.

Agentic risk is discussed as a confidentiality problem — exfiltration, the lethal trifecta, data leaving the boundary. By this model it is marginally more an integrity problem: the agent doing the wrong thing, believing the wrong thing, or executing the wrong code. I5 counts in two rows, which flatters both integrity and availability; even discounting it, the two are level.

I1 is reached by 16 of 20 threats, which means it discriminates almost nothing. That is a true property of agentic systems rather than a modelling defect — data disclosure is the near-universal terminal state — but it has a consequence: severity does not live in this layer. What varies is the data the assessed system actually holds.

Chain reach — impacts by threats they enable

The counterpart to control leverage in the weakness register. An I → T edge exists where the impact supplies a precondition the threat requires — the outcome creates, at runtime, a condition the threat needed and did not have. It is not "bad things follow", and it is not a restatement of W → T: a weakness is a standing property of the system, an impact is a state the system was driven into.

WALKTHROUGHHow to use it

The one part of this document that is genuinely a sequence.

  1. Identify present positions. Walk the architecture against the reference diagram. Does the system retrieve external content (KM)? Invoke tools (TA)? Delegate to other agents (XA)? Face a human directly (HI)? Most systems have RP, KM and TA at minimum.
  2. Add all three planes unconditionally. IA, SC and RT are never scoped out — that is 9 of the 20 threats in scope before you assess a single position. SC's four are assessed against the build and supply band rather than the runtime flow.
  3. Enumerate threats per surface. Each present surface contributes its threats to the candidate list.
  4. Check enabling weaknesses. For each candidate, ask whether its enabling weaknesses are present. A threat whose weaknesses are all mitigated is lower priority; a weakness enabling several threats is a high-leverage control target.
  5. Trace impacts for regulatory-reporting scope. Severity does not come from this layer — I1 is produced by 16 of 20 threats. What varies is the data the assessed system actually holds: personal, regulated, credential, proprietary. Apply that here, at assessment time.
  6. Follow chains. For each impact, ask whether it enables a further threat. This is where single-hop threat models miss agentic attacks. It also tells you where to intervene: an impact sitting in the middle of a chain is an interception point, so containing it closes that route without touching the threat that started it. But count the routes before claiming the control works — most pairs have a direct one as well, which the same containment leaves open. Sandboxing code execution closes RP.1 → I4 → XA.2 and leaves RP.1 → XA.2 running. Only RP.2 has no composed route at all, which is the one place containment achieves nothing and the control must sit at the instruction channel.
  7. Filter by time and origin. build threats route to procurement and CI controls, run threats to runtime controls. autonomous-origin threats need behavioural bounds, not attacker deterrence.
